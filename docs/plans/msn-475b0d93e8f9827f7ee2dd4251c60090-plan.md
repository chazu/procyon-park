# Mission Plan

**Mission:** `msn-475b0d93e8f9827f7ee2dd4251c60090` — Mission archival / retirement
**Repo:** procyon-park

## Intent

Give the operator a way to retire a mission that has been decided (or abandoned)
so it leaves the dashboard's default active board. Introduce a terminal
`archived` mission status — symmetric with doctrine `maturity:retired` — reached
via a new `pp mission archive` verb, and filter archived missions out of the
default Missions panel. The mission list currently grows without bound because
every non-awaiting mission renders in "Other missions" forever; archival lets the
operator clear finished work while preserving the audit trail.

## Success Criteria

1. **CLI verb exists.** `pp mission archive <id> [--repo R]` is registered
   (dispatch branch in `MissionCLI>>runWith:` + reachable via the already-present
   top-level `mission` entry in `Main` `ppCommands` + `printUsage`) and flips a
   mission's `payload.status` to `archived` via a guarded read-modify-write,
   written back through the same signed `putMission` / `/api/bbs/put` upsert the
   other mutations use.
2. **Guard enforced.** Archiving is refused (printed reason, no write) unless the
   mission is in an archivable status: `approved | rejected | researching`.
   `awaiting-approval` is NOT archivable — the operator must approve/reject the
   plan gate first. The refusal message names the current status, mirroring the
   existing awaiting-approval guard.
3. **Terminal semantics.** Once `archived`, a mission cannot be
   approved/rejected/re-archived. The existing approve/reject guards already
   admit only `awaiting-approval`, so `archived` is a sink with no regression.
4. **Status model.** `pp mission list --status archived` works and shows only
   archived missions.
5. **Dashboard default hides archived.** `renderMissionsHtml:`
   (src/api/DashboardSSE.mag) no longer places `archived` missions in the "Other
   missions" group. Default board shows `awaiting-approval` (foregrounded) plus
   non-archived `researching/approved/rejected`; archived render in an optional
   collapsed `Archived` `<details>` section.
6. **Audit trail preserved.** The archived tuple is NOT deleted (missions are
   linear + durable); history stays recoverable via `pp mission list/show` and
   the tuplespace.
7. **Tests.** Unit tests assert: archive succeeds from approved/rejected/
   researching; archive is refused from awaiting-approval; and `renderMissionsHtml:`
   given a mix including an archived mission does not emit that mission in the
   default "Other missions" group. Existing mission tests stay green.

## Research Synthesis

The scout mapped this to a **small, ~3-production-file change**, and the reviewer
independently verified every anchor against source. Consolidated, plan-ready
findings:

- **CLI (src/cli/MissionCLI.mag).** Add an `archive` branch in `runWith:`
  (~line 63–69) plus a `cmdArchive:` method copying `cmdApprove:` / `cmdReject:`
  (~296–306), reusing the signed `putMission:` write (~113). **Critical gotcha:**
  `setStatusFor:to:reason:action:` (~308–334) is **hard-wired** to guard
  `cur = 'awaiting-approval'` (line ~325) and therefore **cannot be reused
  unchanged**. Two options surfaced; the reviewer endorses **Approach A —
  generalize** the helper to take an allowed-from set `{approved, rejected,
  researching}` (over forking a near-duplicate `cmdArchive`), keeping one guarded
  write path. Update `printUsage` (~360) and the lifecycle header comment.
- **Registration.** `mission` is **already** in `Main.mag:11` `ppCommands` and
  `PP.mag:59` dispatch — this is a *subcommand* addition only. **Do NOT touch
  `ppCommands`** (avoids the double-registration failure mode); only add the
  `runWith:` subcommand branch.
- **Dashboard (src/api/DashboardSSE.mag).** `renderMissionsHtml:` (~499–545)
  currently partitions into `awaiting` (~516) and `others` (~518); `archived`
  falls into `others` forever. Add a **third bucket** in the loop (~511–522),
  emit a collapsed `<details>` Archived section, and keep the per-card guard
  (~537–541) and panel `safeRender` (~178) intact. `renderMissionCard:` (~547)
  needs no change.
- **Reviewer-surfaced GAP (must fix).** `renderMissionsHtml:` **early-returns
  "No missions yet"** at DashboardSSE.mag:**523** when *both* `awaiting` and
  `others` are empty. Adding a third `archived` bucket without extending this
  guard means a scope containing **only** archived missions renders "No missions
  yet" and the Archived section never appears. The guard at line 523 MUST be
  extended to also test the archived array — and, per the known Maggie gotcha,
  must be written with **nested** `and:` (`a and: [b and: [c]]`), never chained
  `and:[..] and:[..]` (which parses as the `and:and:` selector → doesNotUnderstand).
- **Criteria that are no-ops (verified by reviewer).**
  - *Criterion #3 (terminal semantics)* needs no work: both the CLI guard
    (MissionCLI.mag:325) and the server `handleMissionDecisionScope:` guard
    (Server.mag:2531) already refuse decisions on any non-`awaiting-approval`
    mission, so `archived` is un-decidable for free. No new server routes needed
    — archive is CLI-only.
  - *Criterion #4 (status allowlist)* is a no-op: **no mission status allowlist
    exists** (`WorkItemFields validStatuses` is work-items only). `cmdList:`
    (~219) already filters by exact string match, so `list --status archived`
    works the moment archived tuples exist.
- **Minor / cosmetic (non-blocking).** `static/dashboard.html:313–315` defines

  `mission-archived` (DashboardSSE.mag:573). An archived pill renders unstyled;

- **Tests.** Extend `test/cli/test_mission_cli.mag` (in-mem `TestMissionCLI`

## Proposed Approach

Ship the smallest change that satisfies the intent, staying on generic BBS
endpoints and mirroring the existing approve/reject mutation shape:

1. **Generalize the guarded write** (Approach A): parameterize
   `setStatusFor:to:reason:action:` with an allowed-from set so both the existing
   awaiting-approval decisions and the new `{approved, rejected, researching} →
   archived` transition flow through one signed `putMission` path. Preserve
   `updated_at` stamping and `--repo`/scope handling.
2. **Add the `archive` subcommand** (`runWith:` branch + `cmdArchive:`), register
   only as a subcommand (no `ppCommands` edit), and extend `printUsage` + the
   lifecycle header comment to `researching → awaiting-approval → approved |
   rejected → archived`.
3. **Partition the dashboard render** into a third `archived` bucket, emit a
   collapsed `Archived` `<details>` section, and — critically — extend the
   line-523 empty-state guard with properly nested `and:` so an archived-only
   scope still renders.
4. **Test the guard and the render**, update the changelog, optionally add the
   `.mission-archived` pill CSS.

## Risks

- **Empty-state regression (highest).** Forgetting to extend the line-523 guard
  hides all missions in archived-only scopes. *Mitigation:* explicit success
  criterion + a render test seeded with only an archived mission.
- **Maggie `and:` chaining trap.** `and:[..] and:[..]` parses as `and:and:`
  (doesNotUnderstand). *Mitigation:* mandate nested `and:` in the guard; call it
  out in the story and in review.
- **Reused-helper breakage.** Generalizing `setStatusFor:to:reason:action:` could
  regress approve/reject. *Mitigation:* keep the default allowed-from as
  `{awaiting-approval}` for decisions; unit-test both paths; existing mission
  tests must stay green.
- **Double-registration footgun.** Touching `ppCommands` when `mission` is
  already registered. *Mitigation:* explicit "subcommand only — do not edit
  ppCommands" instruction.
- **Signed-write / persistence skew.** Unit tests alone don't exercise the signed
  BBS put round-trip. *Mitigation (per doctrine dctr-2d49050f):* pair unit
  asserts with a live end-to-end `pp mission archive` run against a real server
  before considering done.
- **Metrics undercount (informational).** Expect `files_changed`/`duration` to
  under-report (per doctrine dctr-445083c2); judge impact from merge events and
  observations, not skeleton telemetry.

## Definition of Done

- `pp mission archive <id> [--repo R]` archives a mission from `approved`,
  `rejected`, or `researching`, via the signed BBS put, and refuses (with a
  status-naming reason, no write) from `awaiting-approval`.
- `archived` is terminal (approve/reject continue to refuse it) and
  `pp mission list --status archived` lists only archived missions.
- The dashboard Missions panel no longer shows archived missions in "Other
  missions"; they appear only in the collapsed Archived section, and an
  archived-only scope still renders (line-523 guard extended, nested `and:`).
- The archived tuple is preserved (no delete); history recoverable via
  `pp mission list/show`.
- Unit tests cover the guard (all allowed statuses + the awaiting-approval
  refusal) and the render exclusion; the full mission suite stays green; a live
  end-to-end archive round-trip is exercised.
- `CHANGELOG.md [Unreleased]` updated; no new server routes added.
